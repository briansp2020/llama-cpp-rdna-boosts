# The residual verify-step split: a slot that cannot draft at all (TODO #111) -- analysed and DECLINED

Box: 3x R9700 (gfx1201), ROCm 10.1.0.  Models: `Qwen3.8-27B-UD-Q4_K_XL` (qwen35 = hybrid attention + SSM, MTP
head embedded) and `Qwen3.6-35B-A3B-UD-Q4_K_M` for the `-ncmoe` arm.  Server shape (the gate's, unless stated):
`--spec-type draft-mtp-adaptive --spec-draft-n-max 5 -sm tensor -ngl 99 -c 32768 -t 8 --parallel 2 --kv-unified
--cache-ram 0 -fa on`, greedy (`temperature 0`, `seed 42`), `n_predict 400` per request, prompts
`prompts/recall.txt` + `prompts/reasoning.txt` (the host-expert arm uses `prompts/prose-rdna-boosts.txt`).
Every arm runs with `ROCBLAS_USE_HIPBLASLT=0` so cross-process text comparisons are meaningful
(`GREEDY-PURITY.md` §44).

**Outcome: nothing in the delivery changed for this item.**  The residual split is deliberate, its alternative
measures neutral, and there is no correctness at stake.  What did change is the **instrument**: the gate now
counts single-row split steps separately and bounds them (`TAIL_MAX`, default 2 = one per response boundary),
where before they were excluded from the count entirely.  The determinism claim in `GREEDY-PURITY.md` §63 was
corrected (section 3 below).

## 1. What the residual is

r153/r154 (`LLAMA_SPEC_ALIGN`, issue #234) equalize the draft **caps** of the sequences one
`draft-mtp-adaptive` call drafts, which removed 58 split decode steps per 400-token pair.  One step per response
survives, and it is visible only on the host-expert arm:

```
RSPREP prep=1/2 n_tokens=6 n_seq_tokens=6 n_seqs=1 seq_ids=[0]
RSPREP prep=2/2 n_tokens=1 n_seq_tokens=1 n_seqs=1 seq_ids=[1]
...
slot print_timing: id  1 | task 28 | prompt eval time = 981.31 ms / 551 tokens
```

Seq 1 presents a single row because `server_slot::get_n_draft_max()` is
`min(n_ctx - n_tokens - 2, n_remaining() - 1)` and that slot was on its **last token of the response**, so it never
entered the draft call at all — `align_draft_caps()` cannot see a cap of 0 it was never told about.  The
single-row ubatch makes `split_equal()` start a second pass for seq 0's five draft rows.

Split decode steps per arm, from the recurrent memory's `RSPREP` trace
(`LLAMA_RS_ROLLBACK_DEBUG=1`, counted by `scripts/gate-spec-align.sh`'s `splits.awk`, which now reports
`full+tail`: a **draft-length** split — every ubatch >= 2 rows, the defect r153 fixed — and a **tail** split —
one ubatch of a single row, this item):

| arm | knob off (pre-r153) | knob on (= shipped) |
|---|---|---|
| 27B, 2 GPU | `60+0` | `0+0` |
| 27B, 3 GPU | `38+0` | `0+0` |
| 35B-A3B `-ncmoe 40`, 2 GPU | `58+1` | **`0+1`** |
| `ngram-mod,draft-dflash` + DFlash2, 2 GPU | `24+0` | `24+0` (inert by design) |

So this item is exactly the `+1`: one step per response boundary, on the arm where two responses overlap at the
moment one of them ends.

## 2. Why it is declined, not fixed

The candidate fix (implemented, measured and reverted — it exists nowhere in the delivery) is: decide the step's
verify width **before** any draft is set up, and if any generating slot in that step cannot draft, let no slot
draft — the step then verifies one row per sequence and the drafter resumes on the next one.  It removes the
split.  Why it is not worth shipping:

* **No throughput gain, because the two arms do the same number of passes.**  The depth-mismatch case (r153) is
  different: there the second ubatch is pure overhead, so aligning *up* keeps every row and removes a pass, and
  that is worth +23..+30 %.  Here the second ubatch carries the neighbour's **genuine draft rows**, i.e. real
  work: split = `2 passes / ~6 tokens` in that window; suppressed = `1 pass` (1 token) plus the next step's normal
  `1 pass` / ~6 tokens = `2 passes / ~7 tokens`.  Measured with the change behind a temporary A/B switch
  (35B-A3B `-ncmoe 40`, 2 GPU, six alternating pair arms each):

  ```
  half 2 off (split)   agg median 14.9 t/s   runs 14.3 14.9 14.9 14.9 14.9 15.3
  half 2 on  (suppress) agg median 14.9 t/s  runs 14.3 14.9 14.9 15.2 15.2 14.8    (-0.3 %)
  ```

  and on the gate's own arm the r170 and r171-style builds read 159.8 and 160.5 t/s (single runs), i.e.
  indistinguishable.
* **No correctness gain.**  A verify width is a numerics/config axis (`GREEDY-PURITY.md` §63): both arms emit the
  target's own greedy sample at every position, nothing aborts, and the recurrent memory's rollback bound is
  enforced through `n_rs_batch`, not through the ubatch shape — splitting is legal by design and stays reachable
  anyway (content-caused mismatches, prompt/decode mixes, the mixed-drafter chain, and the `LLAMA_SPEC_ALIGN=0`
  arm all still split).
* **It would add a cross-slot coupling for nothing.**  Under it, one slot's draft is suppressed by a neighbour's
  remaining budget, so its verify width — and therefore potentially its text — depends on the other slot's
  timing.  That is the mechanism behind section 3; there is no reason to widen it for a neutral result.

The delivered answer is therefore the **instrument**: `TAIL_MAX` (default 2) bounds the count, so a regression
that manufactures single-row ubatches (a slot that stopped drafting, a slot cut to one row to dodge a mismatch)
fails the gate.  Before this, such a change was invisible — single-row groups were excluded from the split count.

## 3. Finding: the two-slot pair is not run-to-run deterministic (corrects `GREEDY-PURITY.md` §63)

While validating the candidate, the gate's 3-GPU aligned pair produced different text in two runs of the **same**
build, so four runs of one **unchanged** binary were taken:

```
run1  pair: de46c78045/1386  c05fb93d34/1237   agg 159.4
run2  pair: de46c78045/1386  c05fb93d34/1237   agg 158.8
run3  pair: de46c78045/1386  5bf3146c79/1232   agg 174.4
run4  pair: de46c78045/1386  5bf3146c79/1232   agg 173.9
```

Two stable basins, 5 characters apart, with a **9 %** aggregate t/s difference between them — and the candidate
build landed in the same basin as the baseline build, so the basin is a property of the *run*, not of a change.
The alignment is why: it makes one slot's verify width depend on its neighbour's adaptive state and on which rows
share its batch, so an innocent difference in batch composition propagates into a near-tie.  Consequences:

* the run-to-run determinism claim is scoped to **single-slot** arms (which are byte-stable: `alone_a`/`alone_b`
  identical in every run above, and `n_seq == 1` `llama-cli` `b8775233a93a` on/off and across builds);
* a two-slot text diff is not an instrument — which §63 already said for on/off arms, and now says for
  run-to-run too;
* the gate's INFO divergence line moves between runs by design (char 942 and char 34 in two runs of one build),
  and the gate is right not to gate on it.
