# r138 re-base — performance A/B against r137 (2026-10-25, gfx1201)

**Question.** The r138 re-base (`3f03b1772` → `6050b467c`) was gated for *correctness* during the campaign
(per-block build, prefill-logit KLD, op tests, `plain == draft-mtp`, MTP Protocol A) but **no throughput
measurement was taken** for the changes it made — including two adoptions (upstream #31028's one-GEMM
qwen4exp HC path, upstream #29948's `has_fusion` plumbing), a hand-merged MMQ tiling geometry in block 00,
and a restructured `rope.cu`.  This is that measurement.  It was run **after** the `v15-6050b467c-r138` tag
(the release stands on the correctness gates); the purpose is to confirm or refute a regression.

**Outcome: no regression on any arm; dense prefill is 1.4-2.3 % faster.**  No follow-up release needed.

Both configured with the same flags (`GGML_RPC=1 GGML_HIP=ON GGML_NATIVE=1 GGML_HIP_RCCL=1
HIP_PLATFORM=amd GGML_HIP_GRAPHS=ON GPU_TARGETS/AMDGPU_TARGETS=gfx1201 Release`, ROCm 10.1.0,

explicitly on the B side, because an existing build dir keeps whatever set it was first configured with and
that alone changes greedy text (`AGENTS.md`, r138 finding).  Different source *paths* (ccache only); the
r137 binaries are preserved in `~/llama-scratch/build-b137/bin` so the next A/B does not need a rebuild.

**rep 2** (AGENTS: the first `llama-batched-bench` run after a load reads low); rep 1 is in the raw logs and

## What this does **not** cover
