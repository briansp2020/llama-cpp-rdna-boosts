# r138 deep-context prefill sweep (issue #214)

Date: 2026-10-25.  Box: 3x Radeon AI PRO R9700 (gfx1201, ROCm 10.1.0), one GPU used
(`HIP_VISIBLE_DEVICES=0`), ROCm 10.1.0, `~/bin/build-llama-rocm`.

## Why

Issue #214's reporter ran a depth sweep on his 12 GiB RX 6700 XT (gfx1031 as gfx1030,
RDNA2 tile-FA path) at r126 and measured the delivery's lead over upstream shrinking
with depth, crossing at about 80k and reaching -10 % at 120k.  This sweep asks whether
the same shape exists on r138 on the architecture we can measure, in both the resident
regime and the reporter's streaming (`-ncmoe`, no expert-cache arena) regime.

## Controlled load mode (`-lm none -lzm off`, streaming)

`--lazy-mode` is inert here: `qwen35moe` creates no `TENSOR_READ_LAZY` tensor (that flag
governs the PLE/engram table of `qwen4exp`/Flash-Next, `gemma4` and `deepseek41`).  The
load mode is not inert on this cell, because under `auto` (mmap) upstream leaves the
`-ncmoe` host experts in the pageable mapping and prints its own "consider using
`--load-mode none`" warning, while the delivery pins them to `ROCm_Host` regardless.
Pinning the mode on both arms isolates the kernels:

The r138 streaming arm has a ~10 % low cluster (842-844 MiB in the third run and in the
`-lm none` arm) while upstream is stable.  Even the low cluster is +27.5 % over
upstream's best `d120000` (842.19 vs 660.66).  The spread is not the load mode and is
not attributed yet; it does not affect the sign or the shape.

## Conclusion

On gfx1201 there is no upstream crossover at depth on r138.  Resident, the lead is
+18 to +27 % flat across 0..120k.  Streaming with default flags it grows from +18 % to
+45 %; with the load mode pinned it grows from parity at 0 to ~+20 % from 32k on and
stays there.  The default shallow lead is a loader difference (pinned host experts vs
upstream's pageable mapping), not a prefill-kernel difference.

The reporter's gfx1030 crossover is not reproduced here and cannot be measured in the
fleet (no RDNA2 device; the only RDNA2 silicon is an iGPU with no room for the model).
It is tracked as `TODO.md` #106, with the RDNA2 tile configuration and the
`prefill_stages` gate as the candidates.  His clamp-on-streaming finding is fixed in
r138 (r129): a forced-decline config does not clamp `ngram-mod`, a live arena still
does.

## Chunk / VRAM note

The reporter's r126 peak was 260-370 MiB above upstream with the slab declined.  The
slab reserve is not allocated after a decline (it is a sizing subtraction), so it is not
the source.  The compute-buffer chunk is: a slab-declined config still had the slab
*armed*, so `GGML_COMPUTE_BUFFER_CHUNK_MIB` rounded the 510 MiB layout to 768 MiB
(2 x 256 + one spare).  `GGML_COMPUTE_BUFFER_CHUNK_MIB=0` gives 561 MiB (10 % margin),
and both that and `GGML_COMPUTE_BUFFER_MARGIN_PCT=0` give 510 MiB.  The r139 fix gated
the chunk on the slab being live, so the declined arm stays at 561 MiB.  The same cell
on r139 keeps the text identical and the throughput at parity.
