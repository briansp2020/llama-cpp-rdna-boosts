# M0 — what the FA prefill staging is worth, and where its bytes go

**2026-10-27.**  Build `217b1c999` (r158 tip) + a **diagnostics-only** patch
(`DEBUG-stage-decision.patch`, not for the delivery), ROCm 10.1.0, gfx1201 (R9700, 32 624 MiB),
`HIP_VISIBLE_DEVICES` pinned.  All runs sequential.  Gate arms: `-fa on -ctk q8_0 -ctv q8_0 -ub 512`.

## F0. Two measurement traps (both produced a wrong intermediate conclusion here)

1. **`llama-bench` shows no `GGML_LOG_*` output at all.**  `tools/llama-bench/llama-bench.cpp:2345` calls
   `llama_log_set(llama_null_log_callback, NULL)`, so `FA_STAGE`, `SLAB_*`, `moe_cache_report` and every
   other WARN/INFO line is swallowed.  A 27B and a 4B q8_0 `llama-bench` run looked like "the staging
   arena is never used" for exactly this reason.  Use **`llama-cli -v`** (the default verbosity drops even
   `GGML_LOG_WARN`) or `llama-server`.  For throughput use `llama-bench`; for *state* use `llama-cli -v`.
2. **`llama-cli` answers a too-long prompt with exit code 0 and a one-line `srv send_error` on stderr**,
   then does nothing.  Two early runs "measured" a prefill that never happened (0.0 t/s prompt line).
   Check the `[ Prompt: … t/s ]` line before believing an arm.

## F1. The staging *is* the default prefill path on RDNA4 (campaign premise confirmed)

`ggml_cuda_get_best_fattn_kernel` returns `MMA_F16` (debug: `kernel=200`) for a 512-row prefill with a
q8_0 cache, and `ggml_cuda_flash_attn_ext_mma_f16_case` calls
`launch_fattn〈…〉(…, need_f16_K = true, need_f16_V = true, …, FATTN_KV_NATIVE_PER_OPERAND, …)`.
The launcher then decides: wide op (`Q->ne[1] > 8`) **and** `prefill_stages` (i.e. not RDNA3_5) **and** the
operand is native-capable → it **stages** into `fattn_stage[]`; the decode/verify band
(`Q->ne[1] <= 8`) reads the raw cache.  Debug line, 4B q8_0, `-c 8192`:

```
FA_DISPATCH_DBG kernel=200 n_q=2   n_kv=256 ncols1=1     <- band, native read
FA_LAUNCH_DBG  n_q=512 n_kv=512 ncols1=16                <- prefill
FA_STAGE dev=0 stream=0 request=2.0 MiB cached=0.0 MiB alloc=16.0 MiB slab=0
FA_STAGE dev=0 stream=0 request=18.0 MiB cached=16.0 MiB alloc=32.0 MiB slab=0
```

## F2. M0a — what the staging buys (the prize being defended)

Qwen3.8-27B UD-Q4_K_XL (16.34 GiB), **1 GPU**, `llama-bench -p 8192,16384,32768 -n 0 -r 2`.
Arm B forces the native read by lowering the per-operand cap below every real request
(`GGML_CUDA_FA_STAGE_MAX_MB=1` → `stage_cap_K/V` false → `use_native_*` → no staging, no scratch).

| pp | staged (default) | native (`FA_STAGE_MAX_MB=1`) | staged vs native |
|---|---|---|---|
| 8192 | **1324.60 ± 4.53** | 1304.79 ± 4.01 | **+1.5 %** |
| 16384 | **1246.48 ± 0.46** | 1213.84 ± 0.26 | **+2.7 %** |
| 32768 | **1139.94 ± 0.13** | 1085.12 ± 0.17 | **+5.1 %** |

So the staging is worth **real prefill time, growing with depth** (larger than the 150k-era note implied
at 32k), and **outcome B ("drop it") is off the table**.  It is still pure optimisation — the native read
is correct and is what every failure path falls back to.

## F3. Arena sizes follow the formula, on the 3-step ceiling (not the 1.25× ladder)

Same model, `llama-cli -v -c 40960`, 32k-token prompt, `GGML_CUDA_SLAB_STATS=1`:

```
FA_STAGE request=1.0  MiB cached=0.0  MiB alloc=16.0  MiB slab=0
FA_STAGE request=17.0 MiB cached=16.0 MiB alloc=68.0  MiB slab=0
FA_STAGE request=69.0 MiB cached=68.0 MiB alloc=160.0 MiB slab=0
```

* `request` = F16 bytes of `(n_past + n_q)` rows **per operand**, summed over the staged operands.
* `alloc` = `min(hint, 4 × request)` (the r156 ceiling), `hint` = F16 of the cache **root** per operand
  (`40960 rows × 1024 elems × 2 B = 80 MiB` → 160 MiB for K+V).  3 growths, not 14.
* The reporter's `alloc=1024.0 MiB` is the same rule with `-c 262144` (512 MiB/operand cap × 2 operands).

## F4. M0b — the second prize is **not** a decode prize (maintainer's hypothesis, measured)

Qwen3.6-35B-A3B UD-Q4_K_M, **2 GPUs (0,2)**, `-sm tensor -ncmoe 40`, `-c 65536`, 46k-token prompt,
q8_0 KV, `llama-cli -v -n 64` (so `moe_cache`/`SLAB_*` report).  Both arms are slab-armed
(`SLAB_INIT dev=0 free=30.07 GiB … mapped=29.06 GiB boundary=0.56 GiB`).

| arm | `FA_STAGE` | peak `work` / `wide_aux` / `arena` | after the drop | prefill | decode |
|---|---|---|---|---|---|
| staged (default) | 16 → **64 MiB**, `slab=1` | 3200 / 80 / **26560** MiB | `wide_aux=0`, arena **28480** | **2496.6 t/s** | 75.6 t/s |
| native (`FA_STAGE_MAX_MB=1`) | 16 MiB (1st ubatch only) | 3136 / 16 / **26624** MiB | `wide_aux=0`, arena **28480** | 2433.2 t/s | 76.5 t/s |

Readings:

* On a slab config the arena is **already** taken from the slab's wide-phase region
  (`ggml_cuda_slab_wide_aux_alloc`, `slab=1`), i.e. the "generalise the slab" answer is already in the
  tree for the MoE case — it is the *dense* config that has no slab at all (and Windows, where the VMM
  path is unavailable).
* Its slab footprint at the prefill peak is 64 MiB of a 26.5 GiB arena (**0.24 %**), and it is
  **released at the prefill → decode transition** (the `_gen` bump): *after* the drop both arms read the
  same `wide_aux=0 / arena=28480 MiB`.  **So shrinking the staging arena returns nothing to the decode
  arena** — the hypothesis "smaller FA arena → higher hit rate → faster decode" does not hold on this
  shape.  What it *can* buy is prefill-time arena pressure (64 MiB here, up to ~762 MiB at a 200k context
  on the field GSQ config) and the prefill time itself (F2), plus the WDDM/VRAM class behind issue #237.
* Prefill +2.6 % for staged at 46k, consistent with F2.

## F5. What this means for the campaign

* **Keep the staging** (F2) → the target is outcome **A (tile it)**, with **C (bound)** as the fallback;
  the M2 prototype is what decides, on the same three pp points and the arena footprint.
* The *memory* case for tiling is now: the WDDM class (#138/#237/follow-up), the dense/no-slab configs
  (where the arena is a raw `cudaMalloc` outside every manager), the 20-700 MiB of prefill-time arena
  pressure on host-expert configs, and the fact that a per-chunk ring also removes the serial
  whole-prefix conversion pass.
* The *decode* case is **zero** and must not be claimed in the release note (F4).
