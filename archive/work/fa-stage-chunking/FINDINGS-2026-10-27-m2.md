# M2 — the prototype: chunked staging works, but MMA prefill is stream-K-only

**2026-10-27.**  Build `217b1c999` (r158 tip), ROCm 10.1.0, gfx1201 (R9700).  The prototype is
`PROTOTYPE-chunked-staging.patch` (one file, `ggml/src/ggml-cuda/fattn-common.cuh`, +327/-10; applied to a
clean delivery tree, **not** for `patches/`).

## What was built (and it works)

`GGML_CUDA_FA_STAGE_CHUNK=<rows>` (0/unset = off) turns the per-stream FA staging arena into a **ring of 2
slots of `<rows>` KV rows**, and the prefill becomes:

```
for each KV chunk [k0, k1):
    to_fp16_nc  rows [k0, k1) of K and V      -> ring slot (c % 2)
    launch the FA kernel for that KV range    -> unnormalized partial + (max, rowsum)
    acc = online_softmax_merge(acc, partial)  (new flash_attn_chunk_merge)
finalize: KQV = acc / rowsum                  (new flash_attn_chunk_finalize)
```

Chunks are `nbatch_fa`-aligned; every chunk but the last is exactly `rows`, the last absorbs the remainder.
The ring is served by the *existing* arena call (`fattn_stage_try_get(stream, ring_bytes)`), so the slab's
wide-aux home, the `--fit` accounting and `GGML_CUDA_SLAB_STATS` all keep working unchanged.

**Correctness (4B Q8_0, q8_0 KV, `llama-perplexity -c 4096 --chunks 4`):**

| arm | PPL |
|---|---|
| off (baseline) | **6.6302** |
| `CHUNK=4096` (= off by the ≥2-chunk condition) | **6.6302** (identical) |
| `CHUNK=1024` (4 chunks) | 6.6261 (−0.06 %) |
| `CHUNK=512` (8 chunks) | 6.6158 (−0.22 %) |

The drift is the fp16 `VKQ` accumulator being regrouped across chunk boundaries (the same class of numerics
the stream-K split already has) — i.e. a **prefill re-baseline**, not a defect.  Arena: `request=4.0 MiB
alloc=16.0 MiB` for a 512-row ring on the 4B; for the 27B a 2048-row ring is **17 MiB** where the
whole-prefix arena is 160 MiB at 32k and 1024 MiB at 262 144.

## The blocker: requiring the per-output-tile grid costs 2.8x

27B UD-Q4_K_XL, 1 GPU, q8_0 KV, `-ub 512`, `llama-bench -r 2`:

| arm | pp8192 | pp16384 | pp32768 |
|---|---|---|---|
| off (stream-K, the shipped grid) | **1313.89** | **1243.65** | **1140.08** |
| chunked, single chunk (= grid change only) | 836.87 | 620.61 | 411.83 |
| chunked, `CHUNK=2048` | 830.25 | 612.50 | 402.73 |

**The `CHUNK=2048` arm is not slow because of chunking — it is slow because the chunked launch cannot use
the stream-K grid.**  Root cause: the MMA kernel's work decomposition is
`kbc = blockIdx.x * total / gridDim.x` — it never reads `blockIdx.y` or `blockIdx.z`.  The launcher's
non-stream-K grid is `(ntiles_x, parallel_blocks, ntiles_z_gqa·ne12·ne03)`, so a per-tile launch leaves only
`ntiles_x` blocks doing the KV walk and the `z` blocks re-doing the same work.  **MMA prefill is
stream-K-only**; there is no second grid to fall back to.

Two candidate causes were ruled out by measurement:
* the fully-masked-group skip (`GGML_CUDA_FA_MASK_SKIP=0` on the *unchunked* arm: pp8192 1303.96, pp32768
  1143.57 — i.e. **~0**, so disabling it inside a chunk is not the 2.8x);
* the ring itself (the single-chunk arm has no merge and no chunk boundary and is equally slow).

## What that means for the next step (the real work)

Chunking must run **inside the stream-K grid**, i.e. each chunk launch uses the same grid/split/fixup as
today and the fixup must hand back a *per-row unnormalized partial + (max, rowsum)*.  That is a **kernel
protocol change, not a launcher change**, and this session found exactly where it bites:

* the stream-K partials live in two places — `dst` (the block that *starts* a tile, `needs_fixup=false`,
  which **normalizes** its value) and the fixup buffer (`is_fixup`, the tail blocks);
* the fixup kernels fold those into a *final normalized* result, and only visit tiles that have a **seam**;
* a tile whose KV happens to sit inside one block writes a final normalized value and **no meta at all**,
  so a chunked consumer gets a correct-looking number with no `(max, rowsum)` to merge with — which is
  exactly the NaN the first attempt produced.

So the work is: define the per-row `(numerator, max, rowsum)` contract for **every** row (including
no-seam tiles), which means the *first* block of a tile must also publish its meta, and the launcher must
know which rows it already has.  Two shapes are possible:

1. **`kv_start` + "partial" fixup mode** (what was started here): thread one `kv_start` scalar into the MMA
   kernel (used by the group-bitmap index and the `KV_max` bound, so those two exact optimizations keep
   working per chunk — worth ~0 pp on this box, but worth keeping for the multi-slot case), and give the two
   fixup kernels a mode that writes `(numerator, max, rowsum)` element-major for every row.  Needs a
   per-row "already written" convention for no-seam tiles (e.g. the block that writes the final value also
   writes its meta, since `needs_fixup=false` still knows `KQ_max`/`KQ_rowsum`).
2. **Chunk = a stream-K sub-launch with its own fixup into a chunk-major buffer**, then one merge pass.  Same
   protocol requirement; more memory (one partial per chunk) unless merged pairwise.

Either way it is a **one-to-two-day change with a prefill-logit re-baseline**, not a knob: block 05's
`fattn-mma-f16.cuh` + the two fixup kernels + the launcher, gated by `gate-prefill-logits.sh --kv q8_0`
(re-recorded base), `test-backend-ops -o FLASH_ATTN_EXT`, the `W=1..8` probe and pp 2k/32k/64k.

## Verdict for the campaign decision

* The *mechanism* is proven: per-chunk conversion + per-chunk launch + online-softmax merge is
  numerically sound (PPL 6.6302 → 6.6261 at 4 chunks) and takes the arena from O(prefix) to O(chunk).
* The *cost* is entirely in re-expressing the stream-K partial protocol, which is the same code path the
  decode band's purity depends on — the highest-risk file in the delivery for a memory-only win.
* Against that, M0b already showed the **decode** prize is zero (the arena is released at the
  prefill→decode transition), and M0a's +1.5/+2.7/+5.1 % is the value of *keeping* the staging, which the
  chunked arm preserves only if the protocol change does not cost prefill time.

**Recommendation:** park the prototype here and take the decision in the campaign README §0 as **C (bound
it)** for this release cycle: keep the whole-prefix staging (it is worth +1.5-5.1 % prefill) and bound the
arena's *commitment* with the transient-region/`PREALLOC` route from the issue thread, while the
stream-K partial protocol is a separate, deliberate change with its own campaign.  The prototype patch is
kept so that change starts from a working merge/finalize path.
