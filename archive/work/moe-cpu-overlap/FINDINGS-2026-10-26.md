# O0: measured — the MoE "misses" are not where the decode time is (2026-10-26)

**Verdict: PARK the CPU/GPU-overlap feature for the MoE misses.**  O0 was the campaign's own decision
gate ("if the cold read is < 20 % of the token, park this").  Measured on the delivered set (r143) the
cold/miss traffic is **0.1-0.4 % of the decode token** at the auto-sized arena, and **7 %** at the most
extreme arena the cache allows (2048 MiB/device = 6 % residency).  A CPU worker pool computing those
misses beside the GPU could therefore recover at most ~0.1-2 ms of a 28 ms token, for a large amount of
new machinery (per-op host work, CPU numerics mixed into the graph, a graph-capture break at every
`MUL_MAT_ID`).

What the same profile *did* find is in §4-§6: the token is **dispatch-bound, not
memory-bound** — 297 `graph_compute` calls and ~12 000 node dispatches per token, ~13.5 ms of host
time, and the CUDA/HIP graph **never replays** (93 % of calls are refused by the capture-property
check and run the node loop directly).  That is the item worth a campaign.

## 1. What was measured

Box: 2× R9700 gfx1201 on the **PCIe 5.0 x8** root ports (`HIP_VISIBLE_DEVICES=0,2`; GPU 1 is the x4
lane and was deliberately excluded).  ROCm 10.1.0, `~/bin/build-llama-rocm` tree at r143
(`v15-6050b467c-r143`).

Model: `/llm/models/Qwen3.8/Flash-Next/IQ4_NL/Qwen3.8-Flash-Next-IQ4_NL-PROJFIX-*` (qwen4exp,
100.4 GB: 48 layers, **512 experts, 10 used**, expert FFN 640, n_embd 2560).  Expert bytes = 48 × 512 ×
2.64 MiB ≈ **64.8 GB**, so on 2 cards (63.6 GB usable) the host set cannot fit and the expert cache is
the delivery's out-of-VRAM path: **85.4 % slot residency** at the auto arena (55.3 GiB, slab-sized),
99.5 % *access* hit rate once the heat prior/LFRU has warmed.

Command shape (`--ignore-eos` so the generation actually reaches `-n`; the model otherwise stops at ~29
tokens on a plain prompt):

```
HIP_VISIBLE_DEVICES=0,2 llama-cli -m …IQ4_NL… -ngl 99 -sm {layer,tensor} -ncmoe 48 \
  -c 4096 -b 512 -ub 512 -fa 1 -ctk q8_0 -ctv q8_0 -t 12 -C 0x00001ffe \
  -p "The capital of France is" -n 2000 --ignore-eos --temp 0 --seed 42
```

`MOE_EXPERT_HEATMAP_DIR` pointed at a frozen copy of the map with `MOE_EXPERT_HEATMAP=load` so every arm
saw the same prior.  `-t 12` on cores 1-12: the GPU IRQs are pinned to 13,14,15.

## 2. The O0 number (the gate)

| arm | t/s | ms/token | access hit | access miss | expert H2D |
|---|---:|---:|---:|---:|---:|
| `-sm layer`, auto arena (85.4 % residency) | 25.73 | 38.86 | 99.48 % | 0.52 % | 6.6 MiB/tok |
| `-sm tensor`, auto arena | **35.53** | **28.15** | 99.74 % | 0.26 % | 3.3 MiB/tok |
| `-sm tensor`, `MOE_EXPERT_CACHE_MIB=8192` (25 % residency) | 34.04 | 29.37 | 98.71 % | 1.29 % | — |
| `-sm tensor`, `MOE_EXPERT_CACHE_MIB=2048` (6 % residency, the floor) | 34.44 | 29.04 | 95.66 % | 4.34 % | 55 MiB/tok |
| `-sm tensor`, `MOE_EXPERT_HEATMAP=0` (no prior) | 35.27 | 28.36 | 99.16 % | 0.84 % | — |

Read it off the token time: shrinking the arena **14x** (55.3 GiB → 4 GiB, 85 % → 6 % residency, 17x more
miss bytes) costs **0.9 ms of a 28 ms token**.  The routing is extremely concentrated — 6 % of the slots
still serve 95.7 % of the accesses — so the "misses" the campaign was scoped around barely exist at any
arena size this box can create.

The conversion the campaign asked for: 3.3 MiB/token of H2D at this link's measured ~28 GB/s is
**0.12 ms/token** (4.4 % residency arm: 55 MiB = 2.0 ms).  Even the whole PCIe budget is invisible next
to a 28 ms token, which is why the token time is flat across an order of magnitude of arena size.

**A CPU-compute-the-misses arm would gain ~0.1 ms** (and would have to pay a per-op host dispatch to get
it).  This is not a close call, and the "bigger prize on small cards" framing does not survive either:
the concentration is a property of the routing, not of the card, so a 16 GiB card sees the same ~95 %
hit at a proportionally smaller arena.

## 3. Where the 28 ms actually goes (`-sm tensor`, steady state)

`rocprofv3 --kernel-trace`, a 3 s steady window (~106 tokens): **67 % GPU busy, 33 % idle**, ~140 kernel
dispatches/ms.  Shares of the busy time:

| kernel | share | per-token |
|---|---:|---|
| dense mmvq (`mul_mat_vec_q_ksplit`, 3 variants) | 56 % | ~857 dispatches @ 12-14 µs |
| routed MoE (`mul_mat_vec_q_moe`) | 24 % | ~214 dispatches @ 21.5 µs |
| all-reduce (`ggml_cuda_ar_kernel<float,bf16>`) | 15 % | ~143 dispatches @ 19.6 µs |
| `mul_mat_vec_f` (dense f32) | 12 % | |
| lm_head mmvq (`type 14`/Q6_K, 122 µs each) | 12 % | ~19 dispatches |

(Columns overlap because the two devices run concurrent kernels; they are shares of the summed kernel
time, not of wall time.)

The routed-MoE kernel's own average (21.5 µs for 10 experts × 3 matrices) is **not** PCIe-bound at the
delivered residency — 10 × 2.64 MiB = 26.4 MiB of expert bytes per layer per token, of which ~0.26 %
comes over the link.  It is a 21 µs kernel because a single-token expert matmul is latency-bound.

## 4. The host is the bottleneck, not the GPU

`GGML_CUDA_GCDBG=1` (the delivery's own `CUDAGC` instrument), 200 tokens, `-sm tensor`:

```
CUDAGC calls=59344 nodes=2451696 host_total=2780.8ms per_node=1.1us per_call=46.9us
CUDAGC_BREAK pre=84.9ms ev_pre=1.1ms ev_rest=3610.3ms | fuse=691.4ms/738002 fwd=1943.8ms/464512
```

* **297 `ggml_backend_cuda_graph_compute` calls per token** (59 344 / 200), 12 258 nodes/token, at
  **1.1 µs/node → 13.5 ms/token of host dispatch** — half of the 28.4 ms token.
* `ev_rest` (the node loop plus its tail) is 3 610 ms of a 5 705 ms decode (63 %); `ggml_cuda_compute_forward`
  inside it is 1 944 ms; the graph-fusion matcher alone is 691 ms (738 002 calls).
* HIP API trace (steady window): **~124 000 `hipLaunchKernel` calls/s** ≈ 4 100 per token, only ~14
  `hipGraphLaunch` per token.  That is the shape of a pipeline fed one launch at a time.

## 5. The decode graph never replays **on this shape** (proposed campaign: `graph-replay-placement`)

Instrumented `ggml_cuda_graph_compute` (counters in the disposal tree, reverted afterwards):

```
GRAPHCALLS direct=56171 replay=3152 capture=21 propchg=55321      # 200 tokens, -sm tensor
```

**93 % of calls find `properties_changed == true`**, which resets `warmup_complete` and runs the node
loop directly.  That is also why `GGML_CUDA_DISABLE_GRAPHS=1` measures *the same speed* (35.14 vs 35.53
t/s; `host_total` 2863 vs 2788 ms): the graphs are captured and then never replayed, so the delivery gets
no graph benefit at all on this shape.

This is config-specific, not a general defect: r115's own measurement (27B Q8_0, 3 devices, no
`-ncmoe`) saw only 45 captures for a 300-token decode, i.e. the check passed there.  What is different
here is `-ncmoe 48` + the expert-cache arena + the movable-boundary slab — one of them moves a node or
source `data` pointer between otherwise identical tokens.

`ggml_cuda_graph_update_required` compares a full `memcpy` of each node's `ggml_tensor` (plus each
source's `data`/`ne`/`nb`).  Printing the first differing member gives three distinct causes, in order:

1. **`src[]` object addresses** (`field=src`, offset 152) — the Meta (tensor-split) backend rebuilds every
   per-device subgraph from *fresh* simple-tensor objects on each allocation, so a node's source
   *pointers* move while its source *data* pointers, shapes and types stay identical.  Same trap the
   graph **key** was fixed for in r115 (`GGML_CUDA_GRAPH_KEY_DATA`); the property comparison was not.
2. **`name`** — the rebuild also renames nodes (`hc_combine-0` → `hc_combine-4` → `-7`), and `name` is an
   inline `char[GGML_MAX_NAME]` inside the copied struct.
3. **A genuine source data-pointer move** for a minority of nodes once the first two are canonicalised.

Excluding (1) and (2) from the fingerprint (keeping `op`/`type`/`ne`/`nb`/`data`/`view_offs`/`op_params`
and every source's data/ne/nb — the fields a replay actually bakes in) raises the replay count but makes
the run **slower** (28.29 vs 35.23 t/s): with the check passing, the remaining (3) changes trigger
*recaptures*, and a recapture on HIP is a `hipGraphExecDestroy` + `hipGraphInstantiate` (the
`GGML_HIP_GRAPH_FORCE_UPDATE` workaround for the ROCm `hipGraphExecUpdate` executable leak), which costs
more than the direct run it replaces.  Measured 20 captures/token in that arm.

So the fix is not "relax the comparison"; it is one of:

* make the Meta rebuild hand the device **stable** per-device tensor objects (and therefore stable source
  data pointers) for an unchanged graph shape — the real fix, and an infrastructure change;
* or make a recapture cheap enough to be a per-token operation (a `hipGraphExecUpdate` path that does not
  leak on the ROCm in use — needs a driver/version gate, and a soak, because the leak is
  ROCm/rocm-systems#10713);
* or key the replay identity on the *semantic* fingerprint and let the executable be updated rather than
  re-instantiated.

## 6. Second finding: `-sm tensor` is worth +38 % on this shape (config, not code)

26-39 % of the token is the `-sm layer` split: with one device per layer the decode graph is ~50 splits,
each with its own cross-device handoff, and every split pays its own event waits and input copies.  The
same model/config with `-sm tensor` decodes **35.5 vs 25.7 t/s (+38 %)** and shows the same hit rate
(99.74 % vs 99.48 %), i.e. it is not an expert-residency effect.

This is a *documentation/config* finding for out-of-VRAM MoE on 2+ devices (the delivery's tuned path is
`-sm tensor -ncmoe`, and the AGENTS "three-gpu-performance" note records the same direction).  It is worth
a line in `COMMUNITY-CONFIG.md` / the model's `runme`, not a code change: forcing tensor split would
change greedy text on a dense split (AGENTS "Greedy text is a per-device-count reference").

## 7. Reproduce

```
# per-arm throughput (-n 2000 so the arena/heat prior is warm)
HIP_VISIBLE_DEVICES=0,2 MOE_EXPERT_HEATMAP=load MOE_EXPERT_HEATMAP_DIR=<frozen copy> \
  llama-cli -m …IQ4_NL… -ngl 99 -sm tensor -ncmoe 48 -c 4096 -b 512 -ub 512 -fa 1 \
            -ctk q8_0 -ctv q8_0 -t 12 -C 0x00001ffe -p "The capital of France is" \
            -n 2000 --ignore-eos --temp 0 --seed 42 --no-display-prompt --single-turn

# host-side breakdown (the delivery's own counters)
GGML_CUDA_GCDBG=1 … (see above)

# kernel timeline
rocprofv3 --kernel-trace -f csv -d <dir> -- llama-cli …

# graph capture/replay state (needs the counters described in §5; not in the tree)
GGML_CUDA_GRAPH_TRACE=1 …
```

Note the delivery's own traffic line prints `over ~0 tokens` (the token estimate is
`g_takeover / n_tables`, which reads 0 whenever takeovers are not one-per-table-per-token); the MiB/token
figures above were derived from the known `-n` instead.
